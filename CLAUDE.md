# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project intent

Kool.Snack is a restaurant management application, not just a customer-facing menu/ordering site. Access is split cleanly in two: the ordering/reservation flow is fully public (guest checkout, no account ever required), and everything staff-facing (order management, stock, time-clock, kitchen display, team admin) lives behind `/staff/login`. There is no separate backend service — the React app talks directly to Supabase (Postgres + Auth + Realtime + three Edge Functions) as its backend, project `Kool-Snack` (id `pekkeiavgvhgkukzrzqh`, region `eu-central-1`).

**The database schema and RLS policies are not checked into this repo** — there is no `supabase/migrations` directory (the only SQL file in git is `supabase/seed_menu_images.sql`, a one-off data patch), so table shapes and policies must be pulled live via the Supabase MCP tools (`list_tables`, `execute_sql` against `pg_policies`) rather than trusted from memory or grepped from `src/types/`. As of the last check, RLS is the real access-control layer and it's consistent with the client's role gating: `orders`/`order_items` are viewable and updatable by `inhaber`/`manager`/`mitarbeiter`/`kueche` restaurant-wide; `stock_items` are viewable by all four roles but only `inhaber`/`manager` can manage the catalog; `time_entries` are self-only for `mitarbeiter`/`kueche` and restaurant-wide for `inhaber`/`manager`; `profiles` (the team roster) is only listable by `inhaber`/`manager`. Guest orders/reservations are allowed by policy (`customer_id IS NULL` is explicitly permitted on insert) — but insert and select are separate policies, and it's easy to add one without the other: `order_items` and `reservations` both originally had a guest `INSERT` policy but *no* matching guest `SELECT` policy, so a guest could create a row but never read it back (found while building order tracking; fixed by adding `"Guests can view their guest order items"` and `"Guests can view their guest reservations"`, both `USING (customer_id IS NULL)`/`(order_id IN (SELECT id FROM orders WHERE customer_id IS NULL))`). If a new guest-facing read path is added anywhere, check for this same gap before assuming the insert-side policy is enough.

## Roles and auth

- Supabase Auth (JWT-based) provides `session`; a second query to the `profiles` table (by `session.user.id`) provides the app-level `role` column, a Postgres enum: `'inhaber' | 'manager' | 'mitarbeiter' | 'kueche' | 'kunde'`. **The enum values are German, not English** — this project is German-first end to end (UI text, and per explicit instruction, the actual stored values too), so don't reintroduce English role strings anywhere, including in ad-hoc SQL. Both `session`/`profile` live in `AuthContext` (`src/contexts/AuthContext.tsx`). There is no customer-facing login/account UI anymore — `'kunde'` is a vestigial enum value with no reachable sign-up path in this app.
- The enum was originally English (`owner/manager/staff/kitchen/customer`) and was renamed in place via `ALTER TYPE ... RENAME VALUE` (Postgres stores enum literals by OID, so RLS policies, defaults, and views referencing the old names auto-update with no separate fix needed). This rename was *documented as already done* for a while before it actually was — an earlier version of this file asserted the DB was German while the live enum was still English end to end, which silently broke real functionality: the one seeded `inhaber` account failed every `ProtectedRoute` role check except where "manager" happens to be spelled the same in both languages, `handle_new_user`'s hardcoded `'kunde'` insert made every new signup error out, and `order_is_accessible()` (which gates `order_items` inserts) rejected staff-created orders. All of the *application* code — client TypeScript, the three edge functions, and the `handle_new_user`/`time_entry_is_accessible`/`order_is_accessible` Postgres functions — was already written for German; only the enum type itself and the two existing `profiles` rows were still English. The rename has since actually been run and verified (`select enumlabel from pg_enum ... where typname = 'user_role'` → `inhaber, manager, mitarbeiter, kueche, kunde`), so no code changes were needed anywhere — but if role-based access ever seems broken again, verify the live enum labels directly rather than trusting this file's description of them. The one thing a rename does **not** auto-update: any `plpgsql` function body containing the old name as a plain string literal, since those bodies are just text until executed — check `pg_proc` for hardcoded role/status literals if a "not authorized" or "invalid input value for enum" error shows up after a future rename.
- `ProtectedRoute` (`src/components/ProtectedRoute.tsx`) gates every `/staff/*` route (and `/kueche`) client-side by checking `profile.role` against an allowlist, redirecting to `/staff/login` when there's no session. This is a UX guard only — actual enforcement is the RLS policies described above, so don't assume a client-side role check is sufficient security when touching staff data.
- Staff accounts are provisioned via a Supabase **Edge Function**, `create-staff-account`, invoked with `supabase.functions.invoke(...)` from `StaffTeamPage`. Its source is not in this repo (no `supabase/functions` directory) — pull it with the Supabase MCP `get_edge_function` tool before editing, and redeploy with `deploy_edge_function`. It hardcodes its own role allow-list (`ALLOWED_ROLES`) and authorization check (`['inhaber','manager']`), so any future role rename must update this function too, not just the client. It must `UPDATE` the `profiles` row for a newly created auth user, never `INSERT` — the `handle_new_user` trigger already inserts one automatically, so an `INSERT` hits a primary-key conflict and silently rolls back the whole account creation (this was a real, pre-existing bug, found by checking the Supabase `auth` service logs for a `user_signedup` immediately followed by `user_deleted`).
- Public pages never call `useAuth()` and never link to a login screen. Staff reach `/staff/login` out-of-band (a bookmarked URL or a QR code) — there is intentionally no nav link to it anywhere in the customer-facing header.
- **Geofenced QR clock-in**: two more edge functions, same "not in this repo, pull before editing" rule as above. `generate-clock-token` (`verify_jwt: false` — must be callable with no session, since the display kiosk is unauthenticated) takes `{ restaurantId }` and returns `{ token, expiresInSeconds: 45 }`, writing a row to `qr_clock_tokens` and housekeeping-deleting expired ones for that restaurant. `redeem-clock-token` (`verify_jwt: true`, caller must be a staff `profiles` row — allow-list needs the same manual update as `create-staff-account` on any future role rename) takes `{ token, latitude, longitude }`, validates the token (unknown/expired/already-used all reject), then geofences against `restaurants.latitude`/`longitude`/`geofence_radius_meters` (haversine distance, currently 150m around the real Neuss address) before marking the token used and toggling `time_entries` clock in/out for the caller based on whether they already have an open entry. Tokens are single-use — the intended flow is everyone scans the *currently displayed* code, not a saved screenshot.

## Data flow

- App bootstrap (`src/App.tsx`) loads `useRestaurant()` (single row from `restaurants`) and `useMenu()` (parallel fetch of `menu_categories` + `menu_items` + `menu_item_variants`, stitched into a nested category/subcategory/item tree client-side — Supabase's client doesn't do this nesting for you).
- Cart state (`src/contexts/CartContext.tsx`) lives only in `localStorage` (`kool-snack-cart`), not the DB, until checkout.
- **Checkout goes through `create_guest_order()`, never a direct insert.** A security audit proved the previous two-insert flow let anyone order an 18 € dish for 0.01 € — `total_amount` and `unit_price` came from the browser and no policy compared them to the real prices. The `SECURITY DEFINER` RPC now takes only `{menu_item_id, variant_id, quantity, option_ids[]}`, reads every price from `menu_items`/`menu_item_variants`/`menu_item_options` itself, builds the line-item notes from the DB labels, and writes the order atomically (which also fixed the old "order with no line items" risk). The guest `INSERT` policies on `orders`/`order_items` were dropped so the RPC cannot be bypassed — **if you add a new order-creation path, call the RPC; a direct insert will be rejected by RLS.** Cart lines therefore must carry `variantId`/`optionId` (see `src/types/cart.ts`); `unitPrice` in the cart is display-only.
- **Orders carry a human-readable `daily_number`.** Kitchen staff cannot call out "order a3f8b2c1", so `orders.daily_number` is a per-restaurant sequence that resets each service day. It is assigned by the `trg_orders_daily_number` BEFORE INSERT trigger — deliberately a trigger and not logic inside `create_guest_order()`, so the staff POS panel (which inserts into `orders` directly) is numbered too. The counter lives in `order_counters (restaurant_id, service_day, last_number)`, incremented via `INSERT … ON CONFLICT DO UPDATE … RETURNING`; that row lock is what makes concurrent checkouts safe, and a read-then-increment would hand two customers the same number. `order_counters` has RLS enabled with **no policies** on purpose — only the `SECURITY DEFINER` trigger touches it. The service day is computed in the restaurant's own timezone, not UTC. `create_guest_order()` returns the number as a fourth column and `get_guest_order()` exposes it, so the customer sees it immediately rather than after the first poll. Use `formatOrderNumber()` (`src/lib/orderStatus.ts`) to render it — it falls back to a UUID slice so a null can never show as an empty space.
- **Service hours are enforced in the database, not just the browser.** `restaurants.opening_time`/`closing_time` (defaults 12:00/22:00) are checked inside `create_guest_order()`, which raises **SQLSTATE `KS001`** with the message "Wir haben gerade geschlossen" when closed. `CheckoutPage` matches on that code specifically and passes the message through instead of the generic fallback — it is one of the few deliberate user-facing errors, alongside the edge-function strings. The guard covers the **guest path only**: staff take orders in person through the POS panel, which inserts directly and must still work after closing. The client mirror (`src/lib/openingHours.ts` + `useIsOpen`) disables the cart and checkout CTAs, but it is UX only — it is bypassed by changing the device clock, which is exactly why the RPC check exists. Both sides handle a window that wraps past midnight; keep the CASE in the RPC and `isOpenNow()` in step if either changes.
- **Guest order tracking is token-based.** `orders.access_token` is a per-order secret returned by `create_guest_order()`; the customer reads their order only via `get_guest_order(order_id, token)`. The previous policies (`USING (customer_id IS NULL)`) exposed *every* guest order and reservation — name, phone, delivery address — to any anonymous visitor, because that condition is true for all guest rows. Those policies are gone. Consequence: guests have no `SELECT` on `orders`, so **Realtime cannot be used for customer tracking** (it delivers through RLS and can't carry the token) — `useOrderTracking` polls the RPC every 15s instead. Staff Realtime (`useOrders`) is unaffected.
- `ReservationPage` still inserts into `reservations` directly (guest insert is allowed); guests simply cannot read reservations back.
- Order tracking is revisitable, not just a one-time confirmation screen: checkout navigates to `/order-confirmed/:orderId` with router state (`{ orderId, lines, total, orderType, name }`) for the immediate post-checkout render (no extra fetch — `OrderConfirmedPage` uses this directly when `location.state.orderId` matches the URL param). On a page refresh, closed tab, or direct link, there's no router state, so `useOrderTracking` (`src/hooks/useOrderTracking.ts`) fetches the order + `order_items` fresh by id and subscribes to Realtime for the status. The order id is also saved to `localStorage` (`src/lib/orderTracking.ts`, key `kool-snack-last-order`) so `MenuHeader` can show a "Meine Bestellung" link back to it — this is the only way a guest (no accounts) finds their way back to an order after leaving the page.
- Menu item photos: `menu_items.image_url` is the source of truth when set; `src/lib/menuImages.ts` provides a client-side fallback resolver (exact item name → category → regex keyword rules) for rows without one, mirrored by `supabase/seed_menu_images.sql`. Admins can now upload a real photo per dish from `/staff/admin` → Speisekarte (`src/lib/menuImageUpload.ts` → public `menu-images` bucket → writes `image_url`), so the hardcoded fallback map is the legacy path and should shrink over time rather than grow — prefer uploading a photo over adding another entry to `ITEM_PHOTOS`.
- **Bundled images must stay small.** The source photos were once 2–9 MB PNGs each (239 MB in `src/assets`, a 194 MB `dist`) on a mobile-first ordering site; they were bulk-resized to max 1200 px wide and converted to WebP q82, which cut that to 14 MB / 11 MB with no visible quality loss. Any new photo added to `src/assets/` should get the same treatment (≤1200 px, WebP, ideally under ~250 KB) — dropping a raw multi-MB export back in silently undoes this.
- `useOrders` (`src/hooks/useOrders.ts`) is the live order feed used by both `/staff/admin`'s Bestellungen tab and `/kueche` — it fetches `orders` + nested `order_items`/`menu_items`, then subscribes to Supabase Realtime `postgres_changes` on `orders` (filtered by `restaurant_id`) and `order_items` (unfiltered) and refetches on any event. Realtime replication for those two tables was enabled via a Supabase MCP `apply_migration` call (`enable_realtime_orders`) — that migration lives only on the remote project, not in this repo, per the point above.

## Reporting views and the stock ledger

- Five views own their numbers — **read them, don't recompute in JS**: `operations_summary_today`, `attendance_summary_today`, `stock_summary` (one row per restaurant), plus `stock_items_with_status` (`expiry_status`, `is_low_stock`) and `time_entries_with_hours` (`worked_minutes`). The admin dashboard reads the first three through `useDashboardSummary`.
- `stock_movements.reason` is the Postgres enum **`stock_movement_reason`**: `purchase, manual_in, sale_consumption, waste, adjustment, return`. It was previously a `CHECK` constraint with a different four-value list, and the code has been broken **twice** by changing this list to match a document instead of the database. **Verify `pg_enum` before touching `StockMovementReason`** — a value the enum doesn't know is rejected at insert, silently killing every stock booking.
- `stock_items.quantity` can only change through a `stock_movements` insert: the `trg_no_direct_stock_quantity` trigger rejects direct writes (it allows the nested write from `apply_stock_movement()` via `pg_trigger_depth()`). To fix data manually you must disable the trigger, correct, and re-enable.

## Commands

- `npm run dev` — start the Vite dev server with HMR.
- `npm run build` — type-check via `tsc -b` then produce a production build with `vite build`.
- `npm run preview` — serve the production build locally.
- `npm run lint` — run Oxlint (`oxlint`, configured in `.oxlintrc.json`).
- `npm run cap:sync` — `npm run build` then `cap sync` (copies `dist/` into both native projects and re-links plugins). **Any change to `src/` needs this before it shows up in a native build** — the native projects package `dist/`, they don't read `src/`.
- `npm run cap:android` / `npm run cap:ios` — sync, then open the project in Android Studio / Xcode.
- `npm run cap:run:android` / `npm run cap:run:ios` — sync, then build and launch on a connected device or emulator.

There is no test runner configured in this project yet.

On this machine, `node`/`npm` require `C:\Program Files\nodejs` on PATH; this has been added to the user PATH, but if a shell doesn't see it, invoke `npm` via the full path `C:\Program Files\nodejs\npm.cmd`.

## Native app (Capacitor)

The customer-facing app ships as a **native iOS/Android app** built with Capacitor 8, not as a website. `capacitor.config.ts` (appId `de.koolsnack.app`) is the source of truth for the shell; the `android/` and `ios/` projects are generated by `npx cap add` and committed.

- **Building requires the platform toolchain**: Android Studio + JDK 17 for Android, and a Mac with Xcode for iOS. Neither is installed on this Windows machine, so the native projects have never been compiled here — `npm run build` and `npx cap sync` are the furthest this machine can verify.
- **Capacitor 8 draws the WebView edge-to-edge.** `index.html` therefore sets `viewport-fit=cover` (Capacitor logs a warning and reports zero insets without it), and every fixed element pads itself using the `--sat`/`--sar`/`--sab`/`--sal` tokens from `src/index.css`. Those tokens `max()` together `env(safe-area-inset-*)` and the `--safe-area-inset-*` variables that Capacitor's Android `SystemBars` plugin sets on WebViews older than 140 — **never call `env()` directly**, it silently reports 0 on those devices.
- **All native APIs go through `src/lib/native.ts`**, which no-ops on the web so the same components run under `npm run dev`. It owns status-bar styling, splash hide (`launchAutoHide: false` in the config — React hides it after mount so there is no blank frame), haptics, the Android hardware back button, and the `body.keyboard-open` class that hides the fixed bottom bars while the on-screen keyboard is up.
- **Android back is wired to the router** via `useHardwareBack` (`src/hooks/useAppNavigation.ts`). Overlays get first refusal through `src/lib/backStack.ts`: `BottomSheet` pushes its dismiss handler on mount, so back closes the sheet before it touches the route. Any new transient overlay must do the same, or back will navigate out from under it.
- **Geolocation and QR scanning are platform-split.** `src/lib/geo.ts` uses `@capacitor/geolocation` natively and `navigator.geolocation` on the web — this is not cosmetic: `navigator.geolocation` inside a WebView only works if the *host app* already holds the OS permission, and nothing in a web page can request it, so the geofenced clock-in would fail on a fresh install without the plugin path. `src/lib/qrScanner.ts` wraps `@capacitor-mlkit/barcode-scanning` so staff scan the entrance code from inside the app; scanning with the phone's camera app opens the link in a *browser*, losing both the session and the app's location permission. `canScanInApp()` returns false on the web, where the camera → browser round trip still works — and that `isNative` check is load-bearing: the plugin's web `isSupported()` reports **true** wherever `BarcodeDetector` exists, but its web `scan()` is unimplemented and throws, so gating on `isSupported()` alone would show the scan button in Chrome and fail on tap.
- **Native permissions are declared per platform** and must be kept in sync with any new plugin: `android/app/src/main/AndroidManifest.xml` (INTERNET, ACCESS_FINE/COARSE_LOCATION, CAMERA) and `ios/App/App/Info.plist` (`NSLocationWhenInUseUsageDescription`, `NSCameraUsageDescription` — iOS *terminates* the app on a permission request whose purpose string is missing).
- **The iOS project uses CocoaPods, not SPM — this is deliberate, don't "modernise" it.** Capacitor 8 defaults `cap add ios` to Swift Package Manager, but `@capacitor-mlkit/barcode-scanning` (latest, 8.1.0) ships only a podspec and no `Package.swift`, and it pulls `GoogleMLKit/BarcodeScanning`, which Google distributes as a pod. Under SPM the plugin is silently dropped from the build (`cap add` warns "not compatible with SPM") and the app fails to link. The project was therefore regenerated with `npx cap add ios --packagemanager CocoaPods`; if the `ios/` directory is ever recreated, **pass that flag again** or the scanner breaks. On a Mac, run `pod install` in `ios/App` after the first checkout, then always open `App.xcworkspace` — not `App.xcodeproj`.
- **App icons, splash screens and favicons are all generated from one source: `assets/logo.png`** (1024×1024). Regenerate with `npx capacitor-assets generate --iconBackgroundColor '#FFFFFF' --iconBackgroundColorDark '#FFFFFF' --splashBackgroundColor '#FFFFFF' --splashBackgroundColorDark '#FFFFFF'` — never hand-edit the output under `android/app/src/main/res/mipmap-*` or `ios/App/App/Assets.xcassets`. Two things to know: the source logo is an **opaque square with no alpha**, which is why every background colour above is white and why `SplashScreen.backgroundColor` (capacitor.config.ts) and `splashBackground` (android colors.xml) are white too — on the brand red the logo showed as a white box. And the generator writes a `public/manifest.webmanifest` with broken relative paths and an `image/png` MIME on `.webp` files; the committed manifest is a hand-corrected version pointing at `public/icons/*.png`, so don't let a regeneration overwrite it unchecked.
- The in-app logo is `src/assets/kool-snack-logo.webp` (256px, ~12 KB), also derived from the same source. It replaced a 90×90 PNG that was visibly soft at the 56px staff-login size on a retina screen.

## Architecture

- Single-page React 19 app bootstrapped by Vite, using React Router 7 (`BrowserRouter`) for client-side routing and the Supabase JS SDK (`@supabase/supabase-js`) as the sole backend client — there is no custom API server. Entry point is `src/main.tsx`, which mounts `<App />` (`src/App.tsx`) into `#root` in `index.html` inside `React.StrictMode`.
- `src/App.tsx` wraps the whole tree in `AuthProvider` → `CartProvider` → `BrowserRouter` and declares every route:
  - **Public** (no auth, no login UI anywhere in the flow): `/`, `/menu` (the full menu on one screen), `/menu/:slug` (a single category), `/cart`, `/checkout`, `/order-confirmed/:orderId`, `/reservierung`, plus a `*` catch-all (`NotFoundPage` — it matters more in the native shell than on the web, where a bad deep link would otherwise leave a blank screen with no browser chrome to escape from).
  - **Staff** (all wrapped in `ProtectedRoute`, entry point `/staff/login`), except `/staff/pointage-display`: `/staff/pointage-display` (public, no `ProtectedRoute` — meant to run unattended on an entrance tablet; polls `generate-clock-token` every 30s and renders the result as a `<QRCodeSVG>` pointing at `/staff/pointage?token=...`), `/staff/pointage` (personal clock in/out, any staff role — there is no manual clock button, the geofencing *is* the feature. Two ways in: a `token` query param, which is how the web path works when the code is scanned with the phone's camera app, or the in-app scanner button shown on native. Either way it takes a position fix via `src/lib/geo.ts` and calls `redeem-clock-token`, showing the exact result/error — expired/already-used/too-far-away/success. The URL token is stripped with a `replace` navigation once consumed, since tokens are single-use and a refresh would otherwise retry a dead one), `/staff/admin` (`inhaber`/`manager` only — full dashboard: Übersicht/Bestellungen/Lager/Reservierungen/Zeiterfassung tabs, the last one restaurant-wide), `/staff/dashboard` (`mitarbeiter`/`kueche` only — a reduced version of the same shell: Bestellungen/Lager/Reservierungen tabs, no team-wide Zeiterfassung or Übersicht), `/staff/team` (`inhaber`/`manager` only — roster + creates accounts via the `create-staff-account` edge function), `/kueche` (`inhaber`/`manager`/`kueche` only — kitchen display view over the same live order feed, explicitly excludes `mitarbeiter`). `/staff/admin` and `/staff/dashboard` are two different pages/components (`StaffAdminPage`/`StaffDashboardPage`) that happen to share section components (`OrdersSection`, `StockSection`, `ReservationsSection`), not one page with role-conditional tabs.
- `src/lib/supabase.ts` creates the single shared Supabase client from `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY` (see `.env.example`; actual values go in `.env.local`, gitignored). It throws at import time if either env var is missing, so `npm run dev`/`build` will hard-fail without a configured `.env.local`.
- **App chrome is route-driven, not page-driven.** `resolveChrome()` in `src/App.tsx` is a single table deciding which app bar / cart bar / tab bar each route gets; it returns `null` for `/staff/*` and `/kueche`, which render their own full-screen shells and must never show the customer tab bar. Pages do **not** render their own header — add a route to that table instead. `AppBar`, `TabBar`, `CartBar` and the fixed `.action-bar` are the only persistent chrome; the old `MenuHeader`/`Footer` website shell is gone.
- **The same build is a native app *and* a responsive website.** Below the `lg` breakpoint (1024px) the customer side is the phone layout — which is what the native shell always is; from `lg` it presents as a normal desktop site: the bottom tab bar becomes a sticky top nav, the app bar becomes a static page heading, the fixed cart/action bars return to normal flow, sheets become centred dialogs, and cart/checkout go two-column. Content caps at `--content-max` (1200px); the staff back office is deliberately uncapped. See `Design.md` for the full breakpoint table. Two traps worth knowing: `<TabBar />` must stay **first** in `.app`'s DOM (it is `fixed` on mobile so order is irrelevant, but `sticky` on desktop, and sticky cannot lift an element above earlier siblings — as the last child it rendered below the page), and sticky in-page elements must offset from `--sticky-top` rather than hardcoding a bar height, since which bar is above them changes at `lg`.
- **CSS is split four ways, in cascade order** (see `Design.md`, still the design source of truth): `src/index.css` (tokens + primitives only), `src/styles/shell.css` (app bar, tab bar, cart bar, action bar, bottom sheet, stepper, skeletons), `src/styles/screens.css` (customer screen layout), and `src/App.css` (staff back office only — it `@import`s the other two). The legacy `--brand-*`/`--text`/`--bg` token aliases described in older versions of this file are gone; staff-only colours are now `--staff-navy`/`--staff-navy-light`/`--staff-gold`/`--staff-shadow`, scoped in `App.css`.
- **Modals are bottom sheets.** `src/components/BottomSheet.tsx` is the one modal surface (slide-up, drag-to-dismiss, scroll lock, Escape, back-button integration); `ItemSheet` and the staff "Mehr" menu both use it. The old centred `ItemCustomizeModal` was replaced by `ItemSheet`, and the card-grid `MenuItemCard` by the full-width `MenuItemRow`.
- `StaffLayout` renders **two different layouts, not one responsive one**: a navy sidebar above 820px and a bottom tab bar below it, switched by `useMediaQuery`. Nav items with an `onClick` are in-page tabs and fill the bar (first four); items with a `to` are links elsewhere and fall into the "Mehr" sheet along with sign-out.
- `src/contexts/` holds the two app-wide providers (`AuthContext`, `CartContext`); `src/hooks/` holds one-purpose Supabase data hooks (`useMenu`, `useRestaurant`, `useStockItems`, `useTodayTimeEntries`, `useUpcomingReservations`, `useReservations`, `useOrders`, `useOrderTracking`, `useTeam`) plus the UI hooks `useAppNavigation` (scroll restoration, hardware back, keyboard class), `useScrollSpy` (menu category rail) and `useMediaQuery`. There is no manual clock-in hook anymore — `useTimeClock` and its paired `useElapsedTime` ticker were dead code from before the QR/geofence clock-in existed (never imported anywhere) and were deleted; all clock in/out now goes through the `redeem-clock-token` edge function via `PointagePage`. `src/pages/` holds route-level components; `src/components/` holds shared/presentational pieces plus the `/staff/admin` and `/staff/dashboard` section components (`OverviewSection`, `OrdersSection`, `StockSection`, `ReservationsSection`, `TeamTimeSection` — the last is shared between `/staff/admin`'s Zeiterfassung tab and `/staff/team`'s "today's entries" block, don't reimplement it inline); `src/types/` holds the hand-written interfaces mirroring the DB schema (verified live via Supabase MCP, see Project intent).
- **Two different `flattenCategories` exist — don't confuse them.** `browsableCategories()` in `src/lib/menuTree.ts` returns the categories a customer actually browses (a category with subcategories is only a container, so its children are the cards); it backs the home rail, the menu sections and the `/menu/:slug` resolver, which all have to agree for a slug to resolve. `flattenCategories()` in `src/hooks/useMenu.ts` is unrelated: it flattens the same tree into a depth-tagged `{id, name, depth}[]` for the admin category pickers.
- TypeScript project uses project references: `tsconfig.json` points to `tsconfig.app.json` (app source, `src/`) and `tsconfig.node.json` (Vite config *and* `capacitor.config.ts`). Module resolution is `bundler` mode with `verbatimModuleSyntax` and `noUnusedLocals`/`noUnusedParameters` enabled — unused imports/vars fail the build.
- Linting is Oxlint, not ESLint. Rules live in `.oxlintrc.json` (`react`, `typescript`, `oxc` plugins). Type-aware linting is not enabled by default (would require `oxlint-tsgolint` and `"options": { "typeAware": true }`).
- `public/` now holds only generated brand assets: `favicon-32.png`, `apple-touch-icon.png`, `icons/icon-*.png` and `manifest.webmanifest`. The `create-vite` leftovers (`favicon.svg`, the unreferenced `icons.svg` sprite) were deleted. Real menu/UI imagery lives under `src/assets/` (logo, hero, per-category and per-item photos consumed by `src/lib/menuImages.ts`).
